# Managed Memory

## Durable Memory

## 稳定事实
- 支付网关存在上游抖动，导致 `payment-service` 重试耗尽，引发前端持续轮询。
- 前端因支付回执未返回而阻塞加载，造成首屏延迟、页面转圈、`hydration` 耗时增加。
- 商品详情页缓存命中率下降，回源请求增多，提示缓存或上游依赖异常。
- `inventory-db` 连接池使用率接近 95%，空闲连接为 0，`db_connection_wait_time` p95 达 8.2s，存在系统级资源瓶颈风险。

## 约束与偏好
- 当前故障由多链路并发异常叠加所致，支付网关抖动为最可信主因（置信度 0.90），数据库连接压力为高危次因。
- 若支付链路未恢复，应优先考虑临时降级前端轮询机制以缓解用户体验。
- 若数据库连接池持续满载，需立即介入调优参数或排查慢查询/锁等待。
- 所有新事件必须关联 `traceId` 或时间窗口进行全链路比对，避免重复分析。

## 可复用诊断结论
- 支付结果轮询机制在网关不可靠时易引发前端阻塞，属于典型性能雪崩触发点。
- 数据库连接池满是常见性能恶化前兆，常伴随慢查询或锁竞争，需结合执行计划与监控联合分析。
- 多链路指标同步异常（如 `payment_gateway_upstream_latency_p95` 与 `pending_payment_requests` 同升）可作为系统级故障的早期预警信号。

## 待确认项
- `inventory-db` 的慢查询或锁等待是否为连接池积压的根本原因？
- 是否存在静态资源发布或 CDN 策略变更影响前端加载性能？
- 支付链路异常与数据库连接问题是否存在因果关系（如事务阻塞）？
- 降级支付结果轮询机制的可行性及潜在影响范围评估。
