# KB-007 上游依赖错误与波动

## 典型现象

- 订单请求偶发失败，失败点在不同请求里并不一致
- 同一时间窗口里，`payment-service`、`promotion-service`、`product-service` 轮流出现超时
- 日志能看到上游依赖错误，但 traceId 不完整或链路不稳定
- 凌晨窗口更容易出现短时尖峰，几分钟后自动回落

## 常见信号

- `dependency_success_rate` 下降，但没有单一依赖完全失效
- `checkout_failure_ratio` 短时尖峰后快速回落
- 不同下游服务的错误样本交替出现，表现为依赖摇摆
- 证据只覆盖少量失败样本，难以稳定复现

## 判断重点

1. 如果失败点在多个依赖之间摇摆，不要过早锁定单一根因
2. 对“凌晨偶发失败”这类问题，应明确标出偶发、跨服务和低置信度
3. 先给出受影响链路和证据缺口，再决定是否需要继续补查
4. 这种场景更适合保守收口，不要硬凑成数据库或某一个服务的确定性结论

## 建议排查

1. 按时间窗口聚合失败请求，检查最常见的依赖跳点
2. 优先补齐 traceId、requestId 和依赖成功率趋势
3. 对凌晨窗口单独看发布、任务调度、批处理和外部依赖波动
4. 维持低置信度输出，直到证据链能够稳定指向同一故障点
