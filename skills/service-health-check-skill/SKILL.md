# 服务健康检查技能

## 目标

当用户要求“检查系统是否健康”“做一次服务健康检查”“给出健康巡检结论”，或者只是泛化地说“系统好像有点异常”“系统不太对劲”“感觉整个系统有问题”时，用本 skill 给主智能体补充巡检顺序、关注项和输出组织建议。

本 skill 不负责默认 specialist 分诊，也不覆盖 runtime 的最终答案治理；阈值、规则参考和其他案例材料仍通过 knowledge 查询。

## 典型触发说法

- 系统好像有点异常
- 系统不太对劲，帮我看一下
- 整体状态是不是有问题
- 先帮我做一次健康检查
- 看看现在系统是不是健康
- 给我一个巡检结论

## 执行步骤

1. 先明确检查对象、时间范围和关键服务。
2. 优先调用 `queryLogs` 搜索 `error failed timeout Slow query` 等异常信号。
3. 再调用 `prometheus-mcp/queryPrometheusMetrics` 检查 CPU、内存、错误率、P99 延迟等核心指标。
4. 如有依赖异常迹象，再结合 tracing / replay 线索或拓扑相关能力确认是否为下游依赖故障。
5. 当需要阈值参考或补充规则时，再调用 `queryKnowledgeBase` 查询健康检查相关知识，而不是把 knowledge 当作流程模板。
6. 最后把健康检查发现整理成结构化结论，但最终用户答案仍由 runtime 的 final-answer contract 统一治理。

## 判定原则

- 日志里出现明确的 `error`、`failed`、`timeout`，优先判断为不健康。
- 日志里出现 `Slow query`，优先判断为数据库性能异常，不应输出“系统健康”。
- 指标超过阈值时，应明确指出异常项，不要用模糊表述弱化。
- 如果完全没有发现异常证据，才输出“系统健康”。
- 如果证据不足，应说明不足点，不要伪造健康结论。

## 输出组织建议

### 系统健康状态
【系统健康】 或 【系统不健康】

### 诊断结论
一句话说明当前健康状态或主要异常

### 详细说明
- 具体发现的问题：xxx
- 影响范围：xxx

### 建议
1. 具体的可执行建议1
2. 具体的可执行建议2
3. 具体的可执行建议3

## 知识使用原则

- 本 skill 负责给主智能体补充“先看什么、怎么判断、怎么组织说明”的方法资产。
- knowledge 只负责阈值参考、规则说明、案例和手册。
- 不在 skill 中写死具体 `KB-xxx` 文件名作为 contract。
